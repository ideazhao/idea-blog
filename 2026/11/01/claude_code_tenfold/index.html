    2026-11-01 说书匠 书籍 0 Comments

    Boris说：“一个好的计划很重要。”

    编者按：Boris是从0开始一步步把Claude Code养起来的人。

    上篇文章，介绍了怎么上手使用，还记得开发过程中遇到的各种问题吗？

    • AI直接动手做，方案却不是你想要的
    • 执行过程频繁地停顿并索要“权限”
    • 为编码规范，需要多次强调注意事项
    • 上下文过长，导致执行出现偏差

    这些问题，都有现成的标准动作可以帮助解决。

    核心模式

    Plan模式：先讨论再执行

    Boris说：“一个好的计划很重要。”

    他与Claude Code的大多数会话是从Plan模式开始的。作用很明确：只负责规划，不执行。

    Claude Code会告诉你它打算怎么做，但不会修改代码、安装包或运行命令。你可以和Claude Code反复讨论方案，确认后再放手让它去做。

    这个流程的精髓在于：把问题放在方案阶段解决，执行阶段一气呵成。边做边改、反复返工是最浪费词元的用法。

    什么时候该用Plan模式？

    • 不确定实现方案
    • 需改动多个文件
    • 对代码不熟悉
    • 重构或架构级别的大调整

    Auto模式：更安全的“自动驾驶”

    超过90%的权限请求被用户直接批准。因为：

    1、它要做的通常都是需要做的

    2、即便你阻止它，也不知道要让它做什么

    所以，“审批疲劳”让安全机制形同虚设。

    Auto模式就为解决这个问题设计的，其核心思路是由AI分类器替用户判断权限——自动放行安全操作，只拦截危险操作。

    哪些操作可称作“危险”？

    范围升级。用户要求“清理旧分支”，Claude Code把远程分支也删除了。

    凭证探索。Claude Code遇到认证错误，开始自行在环境变量中搜索其他API凭证，试图绕过安全检查。

    数据外泄。Claude Code想分享代码，自行创建了一个公开的GitHub Gist。

    如何启用?

    如果你不是使用的CLI，是桌面端或者插件的话，有更便捷的下拉菜单设置方式。

    权限管理：你来定规矩

    除了Auto模式，Claude Code还有更精细的权限管理——/permissions。

    在此模式下，打开权限管理界面，提前设好“安全护栏”，就可以预先允许Claude Code执行某些操作，它就不会每次都向你确认了。

    会话管理

    Claude Code有上下文窗口限制。对话越长，Claude Code对当前任务的注意力越分散。因此，会话管理至关重要。

    /clear清空

    /clear命令比你想象的更重要。它会清空当前会话的所有对话历史，回到一个干净的起点。Claude Code启动时读取的CLAUDE.md和项目文件不受影响。

    什么时候使用该命令？当你想要开启一个与之前的对话完全不同的任务时。

    /compact摘要

    /compact不会清空对话，而是让Claude Code把当前对话压缩成一份摘要，适合在长会话的中途使用。

    比如你和Claude Code已经讨论了很多内容，上下文太长而影响了性能，但你不想丢失已有结论，使用/compact可以保留关键信息，同时释放上下文空间。

    CLAUDE.md

    用Claude Code写代码，你会接触到很多配置文件，比如package.json、tsconfig.json、.eslintrc等，但有一个文件，比它们加起来都重要，就是CLAUDE.md。

    这个文件是智能体的“宪法”，是智能体了解你的代码库如何工作的主要来源。

    原因很简单：每次启动新会话时，Claude Code做的第一件事就是读取CLAUDE.md文件。

    Claude Code会从中了解项目结构、代码风格、测试命令和常见陷阱等。没有这个文件，Claude Code就像空降到陌生代码库的新人，什么都得从头摸索；有了这个文件，Claude Code一进来就知道规矩。

    那么内容该写什么？一条原则：Claude Code能从代码里读出来的，不要写；Claude Code猜不到的，必须写。

    请注意：不要试图预先写一本完整手册，而是每次Claude Code犯错，就加一条规则。

    Git操作：天然就会

    Git注解：一种代码的版本管理（增删改）工具

    Claude Code对Git的理解不只是帮你执行git命令。它知道你改了哪些文件、在哪个分支上。

    一句话完成commit（提交）和PR（拉取请求）

    Claude Code会分析你的代码变更，生成一个描述性的commit message，然后执行git add和git commit。

    创建PR时，它还会自动生成PR描述，包括改了什么、为什么改。

    Worktree：并行工作利器

    这是Boris首推的技巧。worktree允许你在同一个仓库中checkout（切换并管理）多个分支，每个分支有自己的工作目录。

    --worktree会让Claude Code自动创建一个新的worktree，在一个隔离的目录中工作。这样做的好处是：

    1、不影响当前分支的代码；

    2、可以同时创建多个worktree，分别处理不同的任务；

    3、每个worktree有独立的工作目录，不会互相干扰；

    常见误区

    1、一直在一个会话发指令

    把修复bug、添加功能、重构代码、写文档等全都塞入一个会话，上下文被塞满，会导致Claude Code对每个任务的理解都很浅。

    建议：一个会话聚焦一个任务，完成后使用/clear命令清空会话，或者开启新的终端窗口。

    2、反复纠正，越改越偏

    Claude Code做错了一步，你纠正；改后又在别处出错，你再纠正；纠正多次还是不对。

    建议：若纠正两次仍不对，果断使用/clear命令清空会话，重新描述需求，越具体越好。

    3、过度关注

    每写一个文件你都要看，每改一行代码你都要评论，结果你和Claude Code都很慢。

    建议：关注结果。让Claude Code把一个任务做完，你重点关注最终输出是否符合预期。

    4、需求模糊

    收到“帮我优化一下这个代码”“让这个页面好看点”这样的模糊需求，Claude Code只能靠猜。

    建议：给出具体的、可验证的需求。

    5、不写CLAUDE.md

    项目根目录中没有CLAUDE.md，或者有但从不更新。每次开启新会话都要重新解释项目背景、代码规范、技术选型等。

    建议：认真编写CLAUDE.md，并随着开发进程持续更新。

    掌握此文讲解的技巧，你已经超过大部分开发者，但，还有更强大的能力可以挖掘，我们下期见~
